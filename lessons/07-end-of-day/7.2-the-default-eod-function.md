# Lesson 7.2 - The Default EOD Function

_Module 7: End-of-Day Processing and Persistence. ~15 min_

## Introduction

This lesson checks which end-of-day function the RDB uses, and walks through what the default function does step by step.

## Key Concepts

### Checking for the EOD function

Open `refdata_rdb_reference_a` and go to Instance Params. The `eodFunct` parameter names the analytic that runs at EOD. Unless it has been changed, it is **`dxEODSaveAndDelete`**.

> **Note:** screenshot to be captured: `refdata_rdb_reference_a` Instance Params with `eodFunct` highlighted.

You can find `dxEODSaveAndDelete` in the Analytics Library and open it to read its contents. Treat it as **read-only**. It is part of the KX-supplied DeltaStream package, and editing it would change EOD behaviour for every process that uses it (see the note in Lesson 3.2 about not touching KX packages). If a solution ever needs different behaviour, create a new analytic in your own package and point `eodFunct` at that instead.

### Which tables get saved

The RDB doesn't save every table it holds. It only saves the tables listed in the config parameter named by its `tableEodList` parameter. By default that is `DS_TABLES_EOD_LIST:DEFAULT`.

`DS_TABLES_EOD_LIST` has a single column, `tablesEod`, and the DEFAULT version is empty:

### Walking through dxEODSaveAndDelete

Here is the function in full:

```q
{[dt]
     .log.out[.z.h;"EOD function start ";(dt;.Q.w[]%1e6)];
     .ds.rte.disableGatewayQueries[.ds.cfg.procName];
     .ds.rte.disableGatewayQueries[.ds.cfg.hdbProcess];

     order:desc (tablesEod!count each value each tablesEod);
    {[d;t]
        .log.out[.z.h;("Performing EOD for ",(string t),", date ",(string d));d];
       if[count keys t;() xkey t];
       ![t;();0b;enlist `date];

       if[count[value t] and count complexColumns:where {(0=type x) and (type first x) in 0 99h} each flip value t;
            .[.al.callfunction[`dxEODSaveComplexTable];(d;t;complexColumns);{[t;d;x].pl.report_error_addInfo["Error writing complex table to HDB Dir";(x;.ds.rdb.hdbDir;d;`sym;t)]}[t;d]];
          ];
          if[not count[value t] and count complexColumns;
            @[{[t;d].Q.dpft[`:.;d;`sym;t]}[;d];t;{[t;d;x].pl.report_error_addInfo["Error writing table to HDB Dir";(x;.ds.rdb.hdbDir;d;`sym;t)]}[t;d]];
        ];

        // Clear the local namespace.
         .log.out[.z.h;"Resetting table: ",(string t);()];
        .[t;();:;.ds.schema[t]];
        if[.z.K>2.6; if[0=system"g"; .utils.gc[]]];
        .log.out[.z.h;("Finished EOD for ",(string t),", date ",(string d));(d;.Q.w[]%1e6)];
    }[dt;] each key order;
    // Connect to HDB and reload the dataBase.
    .ds.rte.enableGatewayQueries[.ds.cfg.procName];
    .ds.rte.enableGatewayQueries[.ds.cfg.hdbProcess];

    if[all `~/:.ds.rdb.hdbProcessListDetails@\:`dc_port;:()];
    .utils.hdb.reload1'[.ds.rdb.hdbProcessListDetails @\: `dc_hostport];

 }
```

Taking it in order:

1. **It takes one parameter, `dt`:** the date that has just ended, passed in by the TP's EOD signal. The first log line records that date and the process's current memory use (`.Q.w[]%1e6` converts bytes to megabytes). This makes it easy to see in the logs how much memory EOD freed.
2. **It pauses gateway queries.** `.ds.rte.disableGatewayQueries` is called for both the RDB itself (`.ds.cfg.procName`) and its HDB (`.ds.cfg.hdbProcess`). While data is being moved from memory to disk, a query could see it in neither place or in both, so the gateway is told not to route queries here until EOD is done. Gateways are covered in Module 8.
3. **It orders the tables, largest first.** `tablesEod!count each value each tablesEod` builds a dictionary of table name → row count, and `desc` sorts it so the biggest tables are processed (and their memory released) first.
4. **For each table, it:**
   - **Logs the start** for that table and date.
   - **Unkeys keyed tables** (`() xkey t`). A partition on disk must be a plain (unkeyed) table.
   - **Drops the `date` column** (`![t;();0b;enlist `date]` is a functional `delete`). In a date-partitioned HDB, `date` is a virtual column that comes from the partition directory name, so it isn't stored in the table itself.
   - **Checks for complex columns**: columns whose values are themselves lists or dictionaries (`type` 0 or 99). Plain string columns don't count. If the table has rows and complex columns, it's handed to a separate analytic, `dxEODSaveComplexTable`.
   - **Otherwise, saves it with `.Q.dpft`.** `.Q.dpft[`:.;d;`sym;t]` writes the table as a new date partition `d` under the current directory (the HDB directory, reported in the error messages as `.ds.rdb.hdbDir`). It enumerates symbol columns against the HDB's `sym` file and sorts the table by `sym`, applying the parted attribute for fast lookups. q evaluates right to left, so `not count[value t] and count complexColumns` reads as "not (has rows *and* has complex columns)". As a result, empty tables are still written as an empty partition, which keeps every table present in every date.
   - **Wraps every save in an error trap** (`.[...]` / `@[...]`), so one bad table is reported via `.pl.report_error_addInfo` rather than stopping EOD for the others.
   - **Resets the table to its empty schema** (`.ds.schema[t]`). This is the "delete" in SaveAndDelete.
   - **Runs garbage collection** (`.utils.gc`) if the process is in deferred garbage-collection mode (`\g` = 0), so the freed memory is actually returned, then logs the finish with memory use.
5. **It re-enables gateway queries** on the RDB and HDB.
6. **It reloads the HDB.** For every HDB the RDB is paired with (`.ds.rdb.hdbProcessListDetails`), it calls `.utils.hdb.reload1` with the HDB's host and port so the new partition becomes visible. If none of the HDBs has a port registered (`dc_port`), for example because none is running, it returns without reloading.

### What this means for the course tables

- Both `sampleOrders` and `sampleReferenceData` have a `sym` column and no complex columns, so both are saved with `.Q.dpft` as date partitions.
- After EOD, **both tables are empty in the RDB.** That includes the reference data, so in a real system reference data is typically re-published each day (in our case by dropping a new `sampleReferenceData_<date>.csv` for the file watcher, Lesson 6.7).
- The rows are saved under the date **passed to the function** (`dt`), not the dates in their `time` column.

### Startup and recovery: the other side of EOD

Two other RDB parameters from Lesson 4.3 work alongside the EOD function:

| Parameter | Default | What it does |
|---|---|---|
| initialStateFunct | dxInitialDataState | Runs once when the RDB starts, to initialise its state. |
| logReplayFunct | dxLogReplay | On startup, replays today's tickerplant log, calling `logMsgFunct` (`dxUpdInsertPub` by default) for each logged message. |

Together they explain why restarting the RDB mid-day doesn't lose data. Everything published since the last EOD is in the TP's log for the day, and the RDB replays it on startup. Once EOD has run, the TP rolls to a new log file, so a restart after EOD starts the RDB empty.
