# Lesson 7.5 - Startup and Recovery

_Module 7: End-of-Day Processing and Persistence. ~15 min_

## Introduction

This lesson covers what the RDB does when it starts, and how it gets back the current day's data after a restart.

## Key Concepts

### Startup parameters

Three RDB parameters from Lesson 4.3 control startup:

| Parameter | Default | What it does |
|---|---|---|
| initialStateFunct | dxInitialDataState | Runs once when the RDB starts, to set up its initial state |
| logReplayFunct | dxLogReplay | Replays the current day's tickerplant log at startup |
| logMsgFunct | dxUpdInsertPub | Applied to each message replayed from the log |

Documentation: https://code.kx.com/platform/latest/stream/rdb_template.html

### Recovery from the tickerplant log

The TP writes every message it receives to its log file, in `ENV=DELTADATA_HOME=/DaaSData/tplog` (Lesson 4.3), before publishing it. When the RDB starts, `logReplayFunct` reads that day's log and applies each message with `logMsgFunct`. This rebuilds the RDB's tables as they were before the restart.

This means:

- **A restart before EOD keeps the day's data.** Everything published since the last EOD is in the current log and is replayed.
- **A restart after EOD starts empty.** At EOD the TP rolls to a new log file (Lesson 7.1), and that day's data is already in the HDB.
- **Only published data is recovered.** Data that never went through the TP, such as Module 5's batch load, isn't in the log.

### Worked example

1. Publish the sample files as in Lesson 6.5, and check `count sampleOrders` (5) and `count sampleReferenceData` (4) on `refdata_rdb_reference_a`.
2. Restart `refdata_rdb_reference_a` from the Process Library Status (Lesson 4.5). Leave the TP running.
3. In the RDB's log viewer (Lesson 4.5), look for the log replay lines written at startup.
4. Connect to the RDB again and repeat the counts. They should be unchanged, because the data was replayed from the TP log.
