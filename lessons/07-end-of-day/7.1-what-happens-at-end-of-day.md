# Lesson 7.1 - What Happens at End-of-Day

_Module 7: End-of-Day Processing and Persistence. ~8 min_

## Introduction

This lesson explains why end-of-day (EOD) processing exists and walks through the sequence of events across the TP, RDB and HDB.

## Key Concepts

As covered in Lesson 8.1, the system stores data in more than one place:

- **RDB** (real-time database): holds today's data, in memory
- **HDB** (historical database): holds earlier days' data, on disk

Memory is fast but limited and lost when a process stops. Disk is slower but large and permanent. **End-of-day** is the hand-over between the two. Once a day, everything the RDB has collected is written to disk as a new day in the HDB, and the RDB is emptied, ready for the next day.

### The end-of-day sequence

In our course setup, EOD flows through the three instances created in Lesson 4.3:

1. **The TP decides it's EOD.** When `refdata_tp_reference_a` reaches its `eodTime` (Lesson 4.3), it notifies every subscriber that the day has ended and rolls over to a new tickerplant log file for the next day.
2. **The RDB runs its EOD function.** `refdata_rdb_reference_a` calls the analytic set in its `eodFunct` parameter, passing in the date that has just ended. By default this is `dxEODSaveAndDelete` (Lesson 7.2).
3. **Each table is saved and reset.** For every table listed in the RDB's `tableEodList` config, the RDB writes that day's rows to the HDB directory as a new **date partition**, then resets the in-memory table to empty.
4. **The HDB reloads.** The RDB tells `refdata_hdb_reference_a` (its `hdbProcess`) to reload, and the new date becomes queryable.

### How tables are stored on disk

kdb+ can persist a table in several forms. Which one fits depends on the table's size and how it's queried:

| Form | On disk | Typical use |
|---|---|---|
| Flat file | A single binary file | Small tables where most queries use most columns |
| Splayed | A directory with one file per column | Medium tables (up to ~100 million rows) |
| Partitioned | One splayed table per partition value, usually per date | Large or steadily growing tables, e.g. time-series data |
| Segmented | Partitions spread across several disks | Tables larger than one disk, or that need parallel access |

The default EOD function writes **date partitions**, so after EOD both course tables (`sampleOrders` and `sampleReferenceData`) appear in the HDB under a directory named for the date, with a `date` column you can filter on. This is the most common layout for time-series data.

More detail on each form is in the KX database overview: https://code.kx.com/kdb-x/how_to/interact_with_databases/overview.html

### Delta Platform vs vanilla kdb+

In a vanilla kdb+ tick setup, the TP's `.u.endofday` calls `.u.end` on each subscriber, and the RDB script hand-codes the save and HDB reload: https://code.kx.com/q/architecture/rq/

In Delta Platform the same steps are **configured** on the process instances (`eodTime`, `eodFunct`, `tableEodList`, `hdbProcess`, `directory`) rather than written by hand. Lesson 7.3 covers each of these.

For very large data volumes, data can also be written down during the day (an intraday database, see Lesson 8.1) or replayed from tickerplant logs by a separate log recovery process (DS_LOG_RECOVERY, Lesson 4.1). Both are beyond the scope of this course.
