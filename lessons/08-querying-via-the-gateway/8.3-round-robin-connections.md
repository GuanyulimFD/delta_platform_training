# Lesson 8.3 - Round Robin Connections

_Module 8: Querying via the Gateway. ~10 min_

## Introduction

This lesson introduces what "round robin" means, how a round robin connection group shares load, and when to choose it over the other group types

## Key Concepts

Think of dealing cards around a table: each player gets one card in turn, and when you reach the last player you start again from the first. Nobody is favored and nobody is left out. A **Round Robin** connection group works the same way. Queries are the cards and the databases in the group are the players.

In busy systems many users query at once. If they all land on the same database, that process gets slow while its identical copy sits idle. Round robin spreads the work evenly so that:

- Each database is selected in turn
- Load is spread evenly across all nodes
- No single database is consistently overused

This is achieved by keeping an internal counter for each connection group. It has a list of all of the connections in the group, and it increments this internal counter each time a query comes in. So for example, if there are 3 processes the query could be sent to, running `<counter_value> mod 3` would determine which process to send the query to, and it would reset every 3 queries. In this example, all connections are treated equally, no one connection has priority. If a connection is unavailable, it is skipped and the rotation continues with the next available one.

### Important Distinction

Think Round robin send each query to one database. This is perfect when the databases hold the same data across all of the connections. It is not how you would answer a question that needs data from different databases, such as today's data in the RDB plus historical data in the HDB. For that you would need to send the request to both processes, which is covered in the next lesson.
