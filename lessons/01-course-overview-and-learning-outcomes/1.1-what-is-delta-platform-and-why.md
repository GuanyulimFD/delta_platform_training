# Lesson 1.1 - What Is Delta Platform, and Why Are We Learning It?

_Module 1: Introduction to Delta Platform · ~10 min_

## Introduction

This lesson gives a plain-language answer to two questions before we touch any UI: what is Delta Platform, and what problem does it actually solve compared to building a kdb+ system from scratch?

## Key Concepts

### What Is Delta Platform?

Delta Platform (also referred to as KX Platform, or by its admin console's name, KX Control) is a product built by KX on top of kdb+/q. KX's own documentation describes it as a framework for engineers to "design, build and deploy high-performance, enterprise-grade, data-capture systems." That covers real-time and historical data pipelines used for things like market data capture, surveillance, IoT/sensor data, and other high-volume time-series workloads.

The important word there is *framework*. kdb+/q by itself is a programming language and a database engine. It's extremely fast, but it doesn't come with any opinion about how you structure a multi-process system, deploy it, or let a team of engineers manage it together. Delta Platform is KX's answer to that gap: a managed layer that gives every project a common set of building blocks (processes, packages, messaging, querying) and a UI, **KX Control**, to configure and run them, instead of every team reinventing its own version of the same scaffolding.

You're learning Delta Platform specifically, rather than just "more kdb+," because most client engagements don't involve kdb+ in a vacuum. If a client already has, or is building, a Delta Platform deployment, you'll need to know how to navigate KX Control, how entities are packaged and versioned, and how the platform's own abstractions (process templates, messaging, the gateway) work, on top of your q skills. This course exists to close that specific gap.

### Why Delta Platform? What It Replaces

If you built a real-time tick-capture system in kdb+/q entirely by hand (no Delta Platform, just the language and the database), here's roughly what that would involve:

- Writing and maintaining your own tickerplant, RDB, and HDB scripts (the classic kdb+ "tick" architecture), each started and configured by hand or with your own custom shell scripts.
- Wiring up your own inter-process communication: deciding how processes discover each other's host/port, subscribe to updates, and handle a publisher or subscriber dropping out.
- No built-in config management: parameters for each process live in whatever script or config file you decided to invent, with no shared convention across processes or projects.
- No standard way to package, version, or promote your code between dev/test/prod: that's on you to build (or skip), often via ad hoc scripts or copy-pasting files onto servers.
- If you want a single query to pull together today's data (in the RDB) and historical data (in the HDB), you write that fan-out-and-merge logic yourself, every time, for every query that needs it.
- No centralized UI for an ops team to see what's running, restart something that died, or check logs: that means SSH-ing into boxes and grepping log files.

None of this is *wrong*. It's genuinely how kdb+ systems were built for years, and plenty still are. But it means every team reinvents the same scaffolding, with its own quirks, and onboarding a new engineer means learning that team's particular way of doing things from scratch.

Delta Platform's pitch is that it gives you this scaffolding out of the box: KX's own framing is "enterprise-grade redundancy, load balancing, fault tolerance via multi-process architecture" plus "a complete shared-development environment (code repository, package repository, version control, editor, debugger)" and a "centralized security [and] entitlement-permissioning system." All of that is managed through one UI, rather than hand-rolled per project.

By the end of this course (Modules 2 to 8), you will have used Delta Platform to build exactly the kind of pipeline described above: ingest a file, store it, publish it, and query it back out, using the platform's standard building blocks instead of writing it all from scratch. Lesson 1.2 maps out what those building blocks are and how they fit together, and Lesson 1.3 lays out how the rest of this course gets you there.
